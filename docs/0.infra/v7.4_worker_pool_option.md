## 已对齐的方向(2026-08-01 与 Frank 讨论)

- worker 保持 user 无关(机器是池子资源, mt5_hosts 不加 owner 细分逻辑);
  user↔worker 关系经 strategy_mounts 涌现, 不进 worker 表
- **一个 worker = 机器 + 一个 MT5 账户 = 原子单元**(账户是钱的边界):
  DEMO 池可公用(假钱, magic 归因分开); **LIVE 实质单账户=单租户**, 多用户前必须
  给池加"谁能挂进来"的访问控制(池归属), 而不是给每台 worker 塞 owner
- 1000 用户量级的读写/瓶颈分析见 v8_扩展性读写分析.md

## Frank 的世界观(2026-08-02 澄清, pool 设计必须遵循)

**挂载是唯一意图**("我要这个策略跑在那台 worker"), 策略上的"真金/模拟"不是策略属性,
是它所挂机器的标签**透传**; 机器属于哪个池叫什么都只是标签。
→ 未来形态: 状态标签随挂载机器自动走(挂到哪台, env/世界标签 = 那台机的账户属性),
不再要求人在"策略状态"和"机器角色"两处手工对齐(消灭今天的双钥匙摩擦 —
worker3=demo 而策略=真金挂不上那种)。trades.env 本就由 worker 按自身角色记录,
真正冗余的是 strategies.status 里的世界语义 — 届时 status 回归纯漏斗语义(候选/在跑/淘汰)。

**演进节奏(2026-08-02 Frank 定)**: 现在机器少 = 就是挂载到机器, 机器在什么池就显示什么,
不做任何 pool 机制; 机器多了才引入 pool 概念 — 届时"挂载到 pool"= 系统在池内随便挑一台
可用机器执行(挂载对象从机器升维成池, 挑机逻辑 = 现有"最闲优先"的推广)。

## 归置到本设计一起做的小项

1. **跨角色失效挂载行的归宿**(2026-08-02 Frank 定"无害先不动"):
   DEMO↔LIVE 直切时旧角色挂载行留库 = "落位+挂载点手数"的记忆, 切回秒恢复;
   无害性靠两把钥匙(挂载+状态匹配才认领)。做 pool 时统一决定: 保留(记忆) or
   切换即清(干净) or 显式"落位偏好"字段
2. 挂载手数门槛执法(v0.3 六-2: 门实例最低挂载手数 = 最小手 ÷ 最小倍率 = 0.02) —
   上真金前必须, 挂载/改手数入口统一校验
