## 现状: 哪四条路要反转

| 现有(Linux→Windows) | 反转后(Windows→Linux 外呼) |
|---|---|
| sync 每30s 调 bridge /health 探测 | worker **主动推心跳**(POST /heartbeat) |
| api 拉 bridge /trades 成交 | worker **主动上报成交**(POST) |
| 下载编排拉 bridge K线 | worker **主动上传 K线**(按 api 派的品种任务) |
| /connect 下发账户、/restart 远程重启 | worker **长轮询取命令**(GET /commands, 25s hold) |

Windows→Linux 既有的(announce 注册/runner 拉策略)不变。全部通道统一用 worker_keys
(每机一把)认证 — 单一钥匙覆盖所有路。BRIDGE_API_KEY 随反转退役(不再有入站要保护)。

## 选型: 单向 REST(轮询+推送+长轮询), 否决 socket/WebSocket

**要 REST 的理由(按权重):**

1. **无状态哲学一致(铁律5)**: 每个请求自包含, api/worker 任一侧随时重启, 下一次请求
   即自愈 — 与全系统"状态只在数据库"同构; socket 是有状态长连接, 断线重连/半开检测/
   心跳保活全要自己管;
2. **多副本天然安全(铁律6)**: REST 请求落到任意 api 副本都对(真相在库);
   socket 连接粘在某个副本上, 推命令要解决"哪个副本持有哪条连接"(得加 Redis pub/sub
   一层), 平白多一个服务, 违背铁律7;
3. **延迟需求根本不存在**: 系统硬边界是 bar 级(M1+), runner 本来就是 10~15s 轮询节奏,
   命令延迟=轮询间隔完全无感; socket 的毫秒级推送优势用不上(铁律1 已排除高频);
4. **穿透与运维**: REST 过 NAT/防火墙/代理/ngrok/https 零障碍, 调试=curl;
   WebSocket 在各种中间设备上偶发断流, 排查成本高;
5. **改动最小**: runner 已经是拉模式, 反转只是把四条被动路改成主动发起, 协议不换。

**socket 唯一赢的场景**(亚秒级服务器主动推送)被铁律1明确排除 — 无理由引入。
