# v8 扩展性读写分析(2026-08-01 与 Frank 定 · 备查, 未开工)

> 场景: RDS 单写主库 + 可扩只读副本; 目标规模 1000 用户(默认每用户 2 台 Windows worker
> ≈ 2000 台)。结论先行: **写压力不大(高频的都是小行, 大块的都是批量低频), 要扩的是读**;
> 架构分层(web/api/api-worker/windows 全无状态)天然可横扩, PG 客户端只有 api(2000 台
> worker 零数据库连接, 连接数不爆)。

## 一、写路径清单(全部打主库)

| 写路径 | 谁写 | 1000 用户量级 | 性质 |
|---|---|---|---|
| historical_bars 下载入库 | download worker→api, 临时表 COPY + 主键去重 | **不随用户涨**(K线=共享资产, 只随 品种×券商 涨) | 大块批量写, 年分区已就位 |
| 心跳/健康 mt5_hosts.last_health | 每 worker 30s 一次 | 2000÷30s ≈ 66 写/秒 | 小行高频, 同行 UPDATE |
| trades 回写 + strategy_stats | worker 心跳捎带 | 随成交量, UPSERT 幂等 | 小行中频 |
| strategy_runtime 运行区间 | 节流 5 分钟一写 | ≈7 写/秒 | 小 |
| backtests 结果(trades JSONB 可 MB 级) | api-worker 每单一次 | 随回测算力, 不随用户直接涨 | 大块低频 |
| jobs 队列翻牌 | api-worker/download 抢单 | 批次期间高频小写 | **必须主库**(本质是写) |
| regime_timeline / reconciliations / config / mounts | 低频 | 忽略 | — |

**单写主库结论**: 66/秒小行 + 批量低频大块, 撑 10 倍用户无压力; 写不是瓶颈。

## 二、读路径清单(扩容主战场)

| 读路径 | 量级 | 可走只读副本? |
|---|---|---|
| runner 拉策略(15s/台) | 2000÷15s ≈ **133 req/s** — 且现接口带 LATERAL 最新回测成绩+战绩包(runner 不用, 是 web 复用同接口捎带) | ✅(15s 轮询天然容忍副本延迟) |
| 回测读 M1(一单 20 年 ≈ 700 万行/几百 MB) | 随回测算力涨, **读带宽第一大户** | ✅(纯读历史) |
| web 页面(矩阵/分析/coverage) | 人驱动, 低频单次重 | ✅ |
| jobs 抢单 FOR UPDATE SKIP LOCKED | 高频 | ❌ 必须主库 |

## 三、分层可扩性

```
web         无状态 → 加副本 ✅
api         无状态(心跳看门狗 advisory lock 选主) → 加副本 ✅
api-worker  SKIP LOCKED 抢单 → make scale WORKERS=N ✅(CPU 瓶颈, 加机器)
windows     单机原子(机器+账户), REST 单向 → 随意扩 ✅; 零 PG 连接(客户端只有 api)
pgsql       单写 + N 读副本(RDS)
```

## 四、瓶颈排序(按先撞到的顺序)与修法

1. **runner 拉取接口**(最先撞): 133 req/s × 每次 4+ 查询(含两个 LATERAL 重活)
   ≈ 主库 500+ qps 纯浪费。**修法最便宜**: runner 走轻量拉取(只要 template/params/
   magic/volume/metadata/当日格), web 才用全量版 — `light=1` 参数级改动
2. **回测 M1 读带宽**: 多副本 api-worker 同时抽几百 MB/单。**修法 = 读写分离**:
   api 加只读连接池(RDS reader endpoint), M1 加载/runner 拉取/web 分析走它;
   主库只留写 + jobs 抢单。env 加 `DB_READ_HOST`(缺省=DB_HOST, 单机开发零变化)
   — **唯一的结构性准备**
3. **多券商品种主键(v2.3 老债转正)**: 1000 用户必然多券商, symbols 主键必须加
   broker(现同名品种跨券商挤一行共用 point) — 规模化前必还
4. 心跳/事件写入: 66/秒离红线很远, 10 倍再谈(降频/事件分区), 不预建

## 五、开工顺序(等 Frank 点名, 不预建)

3. v2.3 broker 主键债(多券商启用前)
4. 其余有痛再动

兜底不落代码(DB_READ_HOST 缺省=主库, 不是代码里写死第二地址) ✅。
