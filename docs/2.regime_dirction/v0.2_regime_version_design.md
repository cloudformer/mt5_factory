## 一、表结构

```sql
CREATE TABLE regime_versions (
    id         SERIAL PRIMARY KEY,          -- 版本号: v{id}, 自动编号, 不改不删
    params     JSONB NOT NULL UNIQUE,       -- {"long_ma","short_ma","atr_n","vol_win","vol_q"}
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- regime_timeline 主键升级: (version_id, symbol, date) — 每版本一套完整时间线, 并存互不覆盖
```

- **params UNIQUE = 版本判重的唯一执法**:保存 `200,20,14,252,0.5` 时已存在同参数
  → 数据库撞唯一约束 → 提示"这就是 v1",不新建;新参数 → 插入即诞生 v{新id}
- **版本只增不删**:timeline 挂着它、策略引用着它,删 = 毁证据;存量口径落为 v1
- 数据量:一版本 × 一品种 ≈ 20年 × 260交易日 ≈ 5200 行;10 品种 ≈ 5.2万行/版本,
  几十字节一行 — 存十个版本也是 historical_bars 的零头,随便开

## 二、配置页形态

- Regime 口径配置 = **全局资产(owner 的)**,与数据/品种同待遇,普通用户只读
- 下拉列出全部版本:`v1 · 200/20/14/252/0.5`、`v2 · 200/30/14/252/0.5`…
  选中即**当前默认版本**(存 config,一处)
- "只存不重建"不变:保存出新版本后,去 Regime 页对着该版本显式点重建

## 三、使用方(全部读时现拼, 回测数据零影响)

回测引擎不含 regime,trades 不带格子;贴格是读时 JOIN timeline —— 所以:

- **矩阵页/八格/明细**加版本下拉:同一次回测的 trades,秒切 v1/v2 看归因,不重跑
- **策略引用**(接 metadata 设计,另文):`metadata.regime.version`
  - `= 1` → 贴格/验证/实盘门全按 v1 时间线
  - `= null` → 跟随全局默认版本(默认切换它跟着切;要钉死就写明版本号)
- 验尺实验可用双版本对照:同一批策略在 v1/v2 下各看一遍方向,尺子本身的敏感性白送

## 四、铁律对照

- 命名唯一:版本只有一个叫法 v{id},页面/文档/接口同口径
- 数据库最小化:一张表 + timeline 主键加一维;UNIQUE 判重靠约束不靠代码
- 一切可关联:timeline/策略都挂 version_id 外键,格子→版本→参数一路可 JOIN
- 无状态:版本真相全在库;重建幂等,任何时刻可对任意版本重来

## 五、不做什么

- 不做版本继承/差异对比 UI(要比就两个下拉切着看);不做版本删除/改名;
- 不做每用户口径(全局资产);策略级 metadata(格→手数门)另文讨论后再定。
